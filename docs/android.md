# The Android app (prompt 2, G9)

CampusLink on Android is a **Trusted Web Activity** (TWA): the web app running full screen in Chrome, installed from the Play Store. There is no separate native app to keep in step: every release of the web app is the app. The Android project is generated by [Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) from `apps/android/twa-manifest.json`.

## How it is set up

- **One platform app** (`in.campuslink.app`) opens the bare domain. There the member types their college's address once (the college picker, `apps/web/src/features/reach/college-picker.tsx`); the device remembers it and opens that college next time. "Find your college" on any unknown address goes back to the picker. Nothing lists the colleges: the address the member types answers for itself.
- **Every college host** is in `additionalTrustedOrigins`, so its pages open full screen too. Adding a college means adding its host there and publishing a new version; until then the college still works, in a Chrome tab with an address bar.
- **Digital Asset Links**: every host must serve `/.well-known/assetlinks.json` naming the app and its signing key, or Android shows the address bar. The web build writes the file when `ANDROID_PACKAGE_NAME` and `ANDROID_CERT_SHA256` are set (`apps/web/asset-links.ts`); nginx serves it as JSON on every host (`deploy/nginx/static.conf`). Without those variables there is no file (a 404), and the app falls back to a Chrome tab.
- **White-label apps per college** can come later from the same file: another `packageId`, `host` set to the college's address, its name and colours.

## Environment

| Variable                 | Where                | What                                                                                                                                                                                       |
| ------------------------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ANDROID_PACKAGE_NAME`   | web build            | The app id, `in.campuslink.app`.                                                                                                                                                           |
| `ANDROID_CERT_SHA256`    | web build            | SHA-256 fingerprint(s) of the **app signing key**, comma-separated, as Play Console shows them (`AB:CD:…`, 32 pairs). Include the upload key's too while testing builds you sign yourself. |
| `ANDROID_SIGNATURE_HASH` | WhatsApp template    | The 11-character app hash for one-tap autofill (below). Not used by the code; it goes into the template registration.                                                                      |
| `VITE_ROOT_DOMAIN`       | web build (optional) | The bare domain, so the app shell knows when to show the college picker. Without it, `localhost` and two-label hosts (`campuslink.in`) count as the bare domain.                           |

## Build and publish

1. **Install** Node 20, a JDK 17 and the Android command-line tools; then `npm i -g @bubblewrap/cli`. The first `bubblewrap` run offers to download the JDK and SDK itself.
2. **Edit `apps/android/twa-manifest.json`**: `host` and the icon and manifest URLs to the real bare domain, `additionalTrustedOrigins` to every college's host, and `appVersionCode` (one more than the last release) and `appVersionName`.
3. **Create the upload key once** (keep it outside the repository; `*.keystore` is ignored):
   `keytool -genkeypair -v -keystore android.keystore -alias campuslink -keyalg RSA -keysize 2048 -validity 10000`
4. **Generate and build** from `apps/android/`: `bubblewrap update` (regenerates the Android project from the manifest), then `bubblewrap build`. It signs `app-release-bundle.aab` with the upload key.
5. **Play Console** (play.google.com/console, the college-facing developer account):
   1. Create the app: name CampusLink, free, category Education.
   2. **App integrity → App signing**: use Play App Signing (Google holds the signing key; you keep the upload key). Copy the **SHA-256 certificate fingerprint of the app signing key**: that is `ANDROID_CERT_SHA256`.
   3. **Store listing**: short and full description, screenshots (phone, 2 to 8), the 512×512 icon (`apps/web/public/icons/icon-512.png`) and a 1024×500 feature graphic.
   4. **App content**: privacy policy URL (`https://<a college>/legal/privacy`), data safety (the answers in docs/privacy.md: no ads, no selling data, no trackers; data encrypted in transit; members can ask for deletion), target audience (answer for who actually joins: students under 18 join only with a guardian's consent, docs/specs/phone-identity.md), content rating questionnaire.
   5. **Testing → Internal testing**: upload the `.aab`, add testers, and check on a real phone that pages open **without** an address bar (if there is one, the asset links are wrong: check the fingerprint and that `https://<host>/.well-known/assetlinks.json` returns JSON on every host).
   6. **Production**: promote the release; staged rollout from 20%.
6. **Deploy the web build** with `ANDROID_PACKAGE_NAME` and `ANDROID_CERT_SHA256` before (or with) the first release, so the links verify.

Google's own check: `https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://<host>&relation=delegate_permission/common.handle_all_urls`.

## WhatsApp one-tap autofill for sign-in codes

Prompt 1 sends sign-in codes with WhatsApp's authentication template and a **copy code** button. With the app installed, WhatsApp can instead fill the code in with one tap:

1. **Get the app hash** (`ANDROID_SIGNATURE_HASH`, 11 characters) of the **Play app signing key** (not the upload key): download its certificate from Play Console › App integrity, and compute the hash with the recipe in WhatsApp's "Authentication templates › app signing key hash" documentation (it is the same hash Android's SMS Retriever uses). Check it once on a phone before registering the template.
2. **Register** the authentication template's button as `ONE_TAP` with the package name and that hash (docs/whatsapp-templates.md). The code the API sends is unchanged; members without the app still see copy code.
3. **The app's handshake.** One-tap needs the app to tell WhatsApp it expects a code (an intent to `com.whatsapp` with the `com.whatsapp.otp.OTP_REQUESTED` action) just before it asks for one, and a receiver for `com.whatsapp.otp.OTP_RETRIEVED` that opens the sign-in screen with the code. Bubblewrap generates plain Java, so this is a small addition to the generated `LauncherActivity` and a manifest receiver, kept as a patch beside `twa-manifest.json` and re-applied after `bubblewrap update`. It is **not built yet**: until it is, members tap copy code, as today.

## Known limits

- The TWA uses the phone's Chrome. Phones without a recent Chrome open the site in a Custom Tab, which still works.
- Push notifications reach the app through the web push the site already uses (`enableNotifications` delegates them to the TWA).
- Not tested on a real low-end Android phone over 3G yet (report-2 lists it for you to check).
