# U4 · First run: landing, sign-up and the first ten minutes

Prompt 3, Part U, phase U4. Built on U1's primitives and U2's spaces. Shipped in two parts: **U4a**, the landing page and its speed target, and **U4b**, the three-step sign-up and the first-run checklist on Home.

## Who it is for and the job

A second-year who got the college's link on WhatsApp. In five seconds they should know what this is ("seniors of my college help me get placed"), see what it looks like, and have one obvious button. Two minutes later they should have an account, and within ten minutes something on Home should be about them: their goal, a path they follow, a senior they asked.

## Problems it fixes (§3)

| Problem                                                                                           | What U4 changes                                                                                                              |
| ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| The landing said "alumni guidance network" and showed three icon cards; no picture of the product | An outcome headline, one button, and real screenshots of the demo college, labelled "Demo data"                              |
| The college's crest appeared twice, the eyebrow repeated the app name                             | The crest and name once, in the header                                                                                       |
| "Join with your college email" even where phone sign-up works                                     | "Join with your mobile number" when the college can send codes; email otherwise                                              |

### The speed target: the headline before any script

The F5 measurement showed the headline waited for the page, the scripts, the college and the language pack, the landing's code, then its font. The fix is to stop waiting:

1. `index.html` carries the landing's frame and its English headline (`#fp`, before `#root`, which fills the screen and collapses while the frame shows). `public/boot.js` turns it on before the first paint only when all hold: the address is `/`, the saved language is English (or none), the app is not installed (`display-mode: standalone`), and this device was not signed in last time (`cl:member`, a display hint the session store sets and clears; it holds nothing secret and decides nothing). The launch mark is hidden while it shows.
2. While the app starts, CSS shows the frame only while `#root` still holds the launch mark, so any other outcome (a redirect home, a college error) simply replaces it.
3. The landing **keeps the same headline element**: it renders its header, the rest of the hero, the picture and the sections into the frame's slots (portals) instead of drawing a second headline. A redrawn headline would be a new, possibly larger paint and would move LCP to the app's own render; keeping the element also means no layout shift. Switching language, or leaving the page, removes the frame and the app renders the landing normally.
4. A unit test renders the landing's frame with the English strings and compares it with `index.html`, so the two cannot drift.

Nothing painted later may be larger on the first screen than the headline, or it becomes the LCP element. On a phone the picture starts below the first screen, so the headline stays the largest paint (an e2e test reads the browser's LCP entry on the phone project). On a wide screen the picture sits beside the headline as the brief asks and is the larger paint; it is measured and recorded rather than shrunk to a size that no longer shows the product. Nothing above or around the headline arrives later, so nothing shifts (the same test checks CLS).

```

 I'm a [Student] [Alumnus]            Name [            ]            Sent by WhatsApp to

                                      We use your data to run your   [ _ _ _ _ _ _ ]
 [ Continue → ]                       account and match you with     Didn't get it? Resend in 0:24
 Use email instead                    mentors. Review choices ▸      Send by SMS instead
 Already a member? Sign in            [ Send code ]
```

- **Order**: number and role, then about you, then the code. The brief lists the code second; it is last here because the API checks the code and creates the account in one call (`/auth/phone/verify` with the sign-up fields) and uses the code up when it checks it. Asking for the code before the name would need a new sign-up ticket between the two calls, a session change that rule X10 leaves to the owner (recorded in progress-3.md as an owner decision). Presentation only otherwise: the same fields, the same calls, the same legal behaviour (B2, R1).
- **Consents**: one sentence naming what the defaults do, "Review choices" expands the existing purposes (`ConsentFields`), the required one stays required. Defaults unchanged.
- **Email**: "Use email instead" (staff and colleges without a phone channel) shows email and password in step 1; step 3 is then "Check your email".
- **Minor path**: an under-18 birth month shows a short "What happens next" panel (a parent or guardian confirms; until then the account can read but not message) with the guardian illustration, in the same calm layout; the guardian gate itself is unchanged.
- **Back** keeps what was typed. The progress line is `aria-hidden`; each step's heading says "Step 2 of 3".

Taps for an adult on phone: Continue, Send code, the code fills itself (Android WebOTP) or is typed: 2–3 taps (plus the role chip for alumni and two selects for the birth month), and 4 fields (number, name, birth month, code).

## U4b · First ten minutes (`features/home/setup-checklist.tsx`)

"Set up your CampusLink" on Home for members in their first 14 days, until done or dismissed (per device): at most four rows, each one tap, each done from real data:

| Item                     | Done when                                       | Tap opens                         |
| ------------------------ | ----------------------------------------------- | --------------------------------- |
| Pick your goal           | match preferences have a goal or target company | the goal sheet (`/mentors/prefs`) |
| Follow a career path     | the member follows a path                       | Career paths, "For your branch"   |
| Find a senior            | the member sent a mentorship request            | Find a senior                     |
| Turn on WhatsApp updates | the WhatsApp channel is on in notifications     | the WhatsApp setting              |

A done row says what changed ("Mentors now ranked for: Backend developer"). Alumni get their own three (set availability, add your company, answer a question). Questions are asked when their answer is useful: target companies when Companies first opens; CGPA is never asked of students (it comes from the college record).

## States

- Landing: loading is the first paint itself; the picture has a fixed aspect box, so nothing moves when it arrives; outcomes off is no section at all; a college with no phone channel gets the email button.
- Sign-up: each step validates on Continue; server errors land on the step that owns the field (a wrong code on step 3, a number already in use on step 1).
- Checklist: hidden when all done or dismissed; an item whose data fails to load is left out rather than shown undone.
